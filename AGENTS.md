# AGENTS.md — notes for the AI agent working on this site

This file is for you, the agent. It explains how the site is built, how to
preview it, how to publish it, and — most importantly — **how to work with the
site's owner, who is not technical.** Read this before making changes.

## 1. What this is

`runamile.co.uk` is a personal running blog and training log. It is a **static
site**: plain HTML generated by a small Python script from YAML data files. No
database, no framework, no runtime.

The owner is the runner. He will not read code, run commands, or use git. **You
do all of that.** His job is to describe what he wants; yours is to make it
happen, show him the result, and publish it.

Deliver a great-looking, fast, accessible site. The design was recently
overhauled, so treat the existing look as the baseline — evolve it, don't
gratuitously replace it.

## 2. Map of the repo

| Path | What it is | You edit it? |
|------|-----------|--------------|
| `data/*.yml` | All the content (posts, runs, profile, site settings) | Yes — for content |
| `templates/*.html` | Jinja2 layouts: `base` (chrome), `index`, `blog`, `post`, `about`, `_macros` (shared bits) | Yes — for layout |
| `styles.css` | All the styling. Section 1 holds every colour/type token | Yes — for appearance |
| `generate.py` | Reads YAML + templates, writes `docs/` | Only when adding pages/features |
| `serve.py` | Rebuilds and serves the dev preview on port 8080 | Rarely |
| `docs/` | The **generated** output. Never hand-edit; it is overwritten on build | No (generated) |
| `.github/workflows/pages.yml` | Builds and publishes on push to `main` | No |
| `CNAME` | `runamile.co.uk` — binds the GitHub Pages site to the domain | No |
| `EDITING.md` | The plain-English guide written **for the owner** | Keep in sync |

## 3. The loop you always work in

```bash
# 1. Make the change (usually a data/*.yml or styles.css edit)

# 2. Rebuild and preview
.venv/bin/python serve.py         # serves http://simon.rebecchi.uk:8080
```

- **Always rebuild and check your work before showing it to the owner.**
  ```bash
  .venv/bin/python generate.py      # just rebuilds docs/
  ```
- The dev preview runs on **port 8080** and is reachable at
  **http://simon.rebecchi.uk:8080** (and on the LAN at
  `http://192.168.1.124:8080`). Give the owner the
  `simon.rebecchi.uk:8080` URL — that is the address he knows.
- Never tell the owner to run commands. Run them, then hand him a link.

## 4. Going live — how publishing works

The live site at **https://runamile.co.uk** is rebuilt automatically by GitHub
Actions whenever `main` is pushed. There is no manual deploy step and nothing
to click on GitHub.

**So "publishing" means exactly this:**

```bash
git add -A
git commit -m "Short description of what changed"
git push origin main
```

Within a minute or two the change is live at runamile.co.uk. To confirm, give
it a moment and fetch the live page, then check that your change is present:

```bash
curl -s https://runamile.co.uk/ | grep -i "something you just added"
```

The build runs on GitHub, so it takes ~1 minute to appear. You can watch runs
at https://github.com/Simreb176/run-a-mile/actions (or with `gh run list`, if
the `gh` CLI happens to be installed — it is not required).

If a run fails, the usual cause is a YAML typo in `data/`; the build log names
the file and line. Fix it, commit and push again.

> First-time setup already done: the repo exists, Pages is set to
> **GitHub Actions**, the `CNAME` file points at `runamile.co.uk`, and DNS is
> pointed at GitHub. You should not need to touch any of that.

## 5. Working with the owner (this is the important part)

He is the ideas person; you are the hands. Keep these habits:

- **Never show him a command, a file path, or an error message and leave it at
  that.** Do the work, then describe the *result* in plain language.
- **Always preview before publishing.** After a change say something like:
  *"I've changed it. Have a look at simon.rebecchi.uk:8080 — the latest posts
  now sit in cards with a bit more breathing room. Happy?"*
- **Publish in small steps.** One change at a time, confirmed by him, then push.
  Small pushes are easy to undo.
- **Explain what's possible, not just what he asked for.** He doesn't know the
  menu. When relevant, offer concrete options, e.g.:
  - *Appearance:* colours, fonts, rounded vs square corners, light/dark, wider
    or narrower pages, photo banner at the top.
  - *Structure:* add pages (a "Races" page, a "Kit" page), a photo gallery,
    an FAQ, a map of routes, a subscribe form.
  - *Content:* posts with headings, quotes, images and lists; a searchable log;
    weekly/monthly summaries generated from the log.
  - *Niceties:* automatic "X km run this month" totals, share previews for
    Facebook/WhatsApp, a favicon, email contact link.
- **When he's vague, show don't ask.** Render two options and let him pick,
  rather than interrogating him about CSS.
- **Write his words, not yours.** For posts and the About page, use his text
  verbatim. Fix only obvious typos; never invent running history.
- **Guard his data.** Before a destructive change, commit what's there so it
  can be restored. Never rewrite pushed history.

### A short script you can reuse when he asks "so how does this go live?"

> "You write it, I build it, GitHub publishes it. I make the change on your
> computer, show it to you at simon.rebecchi.uk:8080, and once you're happy I
> send it up — the real site at runamile.co.uk updates itself about a minute
> later. You never have to run anything or type a command."

## 6. Where things live, for common requests

- **Add a post** → new block at the top of `data/posts.yml`
  (`date`, `title`, `slug`, `body`). Markdown works in `body`.
- **Log a run** → new entry at the top of `data/training.yml`.
- **Change name/tagline/intro/goal/stats** → `data/profile.yml`.
- **Change title, description, email, social links** → `data/site.yml`.
- **Change colours, fonts, spacing** → `styles.css`, section 1 (the tokens).
- **Change the header, footer, or nav** → `templates/base.html`.
- **Change the home page** → `templates/index.html`.
- **Add a whole new page** → create `templates/<name>.html`, add it to `PAGES`
  in `generate.py`, and add a link in the nav in `templates/base.html`.

### YAML rules that bite (check these when a build fails)

- Indentation is significant — match the block above exactly.
- **Quote time values**: `"32:15"` not `32:15` (unquoted, YAML reads it as a
  sexagesimal number).
- `date:` must be `YYYY-MM-DD`.
- `slug:` is the URL: lowercase, hyphens, no spaces, never reuse one.

## 7. Definition of done

1. Site builds: `.venv/bin/python generate.py` prints no errors.
2. Preview looks right at http://simon.rebecchi.uk:8080, including the blog
   list, a single post page, and the about page on a narrow screen.
3. Links and stylesheet resolve on **post pages** (they live at
   `/posts/<slug>/`, so every link must be prefixed with `base`).
4. `EDITING.md` updated if you changed anything the owner can now edit.
5. Committed and pushed, and the live site (or the Actions page) shows the
   change within a minute or two.
